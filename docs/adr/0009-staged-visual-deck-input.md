# ADR 0009: 新規Visual Deckを段階入力で作成する

## 状態

採用

## 背景

一部のBedrockモデルは、最大50ページの`VisualDeckSpec`を1回で受け取る作成ツールに対し、必須データを省略した空呼び出しを先行する。従来は空入力へ`input_required`を返して回復させ、その後にData Annotationsの`Required`を追加して公開MCPスキーマでも`deck`を必須にした。

しかし、LibreChatとClaude Opus 5の通しE2Eでは、スキーマを必須化した後も最初の作成呼び出しが`{}`となり、クライアント側のスキーマ検証で拒否された。完全仕様を一度に生成する負荷そのものを小さくしなければ、空呼び出し、再試行、再帰回数の消費を安定して防げない。

## 決定

- 完全な`VisualDeckSpec`を1回で受け取る新規Visual Deck作成ツールは公開しない。
- 新規生成を次の段階へ分割する。
  1. `pptx_start_visual_deck`: タイトル、完成ページ数、テンプレート、テーマ、デザインを登録して固定する。
  2. `pptx_add_visual_slides_to_draft`: 連続した完成済みスライドを1〜4ページずつ追加する。
  3. `pptx_finish_visual_deck`または`pptx_finish_branded_visual_deck`: ドラフトIDだけを受け、既存の生成ジョブへ確定済み仕様を渡す。
- ドラフトはメモリ内に最大128件保持し、1時間で失効させる。MCPプロセス再起動時は復元せず、モデルへ新規開始を求める。
- ドラフトは信頼済みHTTPヘッダーから得た利用者と会話の両方で分離し、別利用者・別会話から参照できないようにする。
- 開始時の完成ページ数とクリエイティブ方針、最大4ページのバッチ上限、全ページ揃ってからのfinishをサーバー側で強制する。`startSlideNumber`は省略時にサーバーが算出し、明示時だけ正しい次番号との一致を検証する。受理済みバッチの再送は拒否する。
- 各段階で動作上必須の引数へData Annotationsの`Required`を付け、公開MCPスキーマの`required`配列を回帰テストする。ただし、値域と業務規則はドメイン層でも検証する。
- 既存資料へのページ追加は段階ドラフトを開始せず、`pptx_insert_visual_slides`へ追加分だけを渡す。

## 結果

モデルが1回で生成するツール入力は最大4ページに限定され、6〜50ページの資料でも巨大なJSON引数を一度に構成する必要がなくなる。サーバー側で順序と完成数を保持するため、受理済みページの重複や欠落をジョブ投入前に検出できる。

一方、ドラフトはメモリ内状態であるため、作成途中にMCPを再起動すると失われる。また、ページ数に応じてツール呼び出し回数は増える。これは巨大入力の空呼び出しと不安定な再試行を避けるための意図したトレードオフである。

Data Annotationsは公開スキーマへ影響するが実行時検証を代替しない。空文字、空配列、値域、順序、所有権、完成状態は引き続きサーバーで検証する。

生成成功後の再開始、失敗時の再試行回数、修正ジョブの直列性は [ADR 0012](0012-visual-deck-workflow-guardrails.md) で定義する。

## 検証

2026-08-05のLibreChat／Claude Opus 5通しE2Eでは、Web調査を含む6ページの新規資料が、`start` 1回、4ページと2ページの`add`各1回、`finish` 1回で生成された。すべてのPowerPointツール呼び出しに必須入力があり、空の`{}`、スキーマエラー、`input_required`は発生しなかった。全6ページのプレビュー取得後、文字密度の高い1ページを単ページ修正し、再プレビューとPPTXダウンロードまで完了した。
