# ADR 0005: BedrockではVisual Deckを1ページずつ修正する

## 状態

採用

## 背景

Claude Opus 5とLibreChatの通しE2Eで、全ページの画像評価と問題ページの特定までは成功した。一方、複数の完全な`VisualSlideSpec`を`revisions`配列へまとめる修正では、Bedrockが`jobId`だけを送って修正内容を省略し、`input_required`後も同じ呼び出しを繰り返した。4ページを同時に直す入力は、通常の生成後ターンとして大きすぎる。

## 決定

- `pptx_refine_visual_slide` は必須の`revision`を1個だけ受け取る。
- `jobId`の既定値を`latest`とし、信頼済み利用者・会話境界内の最新成功Visual Deckをサーバー側で解決する。
- 複数ページはジョブの成功を確認しながら逐次修正する。最新成功ジョブの仕様を次の入力に使うため、既適用の修正と企業テンプレートは累積する。
- 各単一ページ修正はサーバー内で最大30秒だけ完了を待つ。最終状態を直接返せた場合は`pptx_get_job`を省略し、LibreChatのグラフステップ消費を抑える。30秒を超えた場合だけ従来どおりジョブ受領情報を返す。
- 一括`pptx_refine_visual_deck`は、完全な配列を安定して送れるクライアント向けに維持する。

## 結果

1回の構造化入力が1ページ分に限定され、Bedrockの引数省略と再試行ループを避けやすい。複数ページの修正ではジョブ数が増えるが、成功時の状態確認を各ページ2〜3回行う必要がなくなり、最大2巡の視覚リフレクションをLibreChatの再帰上限内へ収めやすくなる。
